# Интеграционное тестирование инструментов Files и Git

Проведи интеграционное тестирование инструментов категорий `Files` и `Git` в текущем `WorkspaceRoot`.

Работай последовательно. После каждого этапа остановись и выдай краткий промежуточный отчет:

- что проверено;
- какие инструменты вызваны;
- что прошло успешно;
- какие ошибки обнаружены;
- можно ли переходить к следующему этапу.

Цель — проверить фактическое поведение инструментов.

## Этап 1. Подготовка

1. Проверь структуру `WorkspaceRoot`.
2. Убедись, что доступен Git-репозиторий.
3. Зафиксируй начальное состояние через `git_status`.
4. Проект является тестовым, поэтому все операции можно выполнять с существующими файлами, находящимися внутри `WorkspaceRoot`
5. Все дальнейшие файловые изменения выполняй только внутри `WorkspaceRoot`.

После этапа выдай отчет.

## Этап 2. Files — чтение и навигация

Проверь:

- `list_files`;
- `find_files`;
- `read_file`;
- `search_text`.

Проверь:

- обычные пути;
- вложенные пути;
- поиск текста;
- поиск файлов;
- диапазоны строк;
- отсутствующий файл;
- попытку выхода через `..`;
- абсолютный путь;
- обращение к `.git`;
- sensitive path, если можно проверить безопасно.

После этапа выдай отчет.

## Этап 3. Files — изменение

Проверь:

- `create_directory`;
- `apply_patch`;
- `copy_file`;
- `move_path`;
- `delete_file`;
- `delete_directory`.

Проверь:

- создание нового файла;
- изменение существующего файла;
- неоднозначный `oldText`;
- отсутствующий `oldText`;
- копирование;
- перемещение;
- удаление файла;
- удаление каталога;
- конфликт destination;
- попытку выйти за `WorkspaceRoot`;
- approval для destructive operations.

После этапа выдай отчет.

## Этап 4. Git — read-only инструменты

Проверь:

- `git_status`;
- `git_history`;
- `git_diff`;
- `git_blame`;
- `git_show`;
- `git_branch`;
- `git_tracked_files`;
- `git_check_ignore`;
- `git_remote`.

Используй файлы проекта.

Проверь:

- корректный результат;
- отсутствующий path;
- untracked path;
- invalid ref;
- пустую историю, если сценарий возможно изолировать;
- отсутствие утечки raw stderr;
- structured errors;
- соблюдение `WorkspaceRoot`.

После этапа выдай отчет.

## Этап 5. Git — staging и commit

Проверь:

- `git_stage`;
- `git_commit`.

Сценарий:

1. Создай новый файл.
2. Измени существующий файл.
3. Удали tracked-файл.
4. Выполни `git_stage` для конкретных путей.
5. Убедись через `git_status`, что staged только нужные файлы.
6. Выполни `git_commit`.
7. Проверь commit через `git_history` и `git_show`.

Отдельно проверь:

- literal path вместо произвольного pathspec;
- directory path;
- ignored file;
- отсутствующий path;
- sensitive path;
- commit без staged changes.

После этапа выдай отчет.

## Этап 6. Git — branch switching

Проверь `git_switch_branch`.

Сценарий:

1. Создай новую тестовую ветку.
2. Проверь её через `git_branch`.
3. Сделай commit в тестовой ветке.
4. Переключись на исходную ветку.
5. Переключись обратно.

Отдельно проверь:

- `create=true`;
- `create=false`;
- отсутствующую ветку;
- попытку создать уже существующую ветку;
- dirty tracked worktree;
- отсутствие remote guessing.

После этапа выдай отчет.

## Этап 7. Git — restore

Проверь `git_restore`.

Сценарии:

- restore из `index`;
- restore из `HEAD`;
- restore из конкретного `ref`;
- несколько exact paths;
- восстановление удаленного файла.

Проверь обязательный approval:

- подтвержденный restore;
- отклоненный restore;
- изменение файла между запросом approval и выполнением, если сценарий возможно воспроизвести.

Убедись, что restore working tree не изменяет index, если это не предусмотрено операцией.

После этапа выдай отчет.

## Этап 8. Git — stash

Проверь `git_stash`.

Сценарий `push`:

1. Создай staged и unstaged изменения.
2. Выполни stash.
3. Проверь approval.
4. Убедись, что изменения сохранены и worktree/index приведены в ожидаемое состояние.

Сценарий `apply`:

1. Применить созданный stash.
2. Проверить восстановление файлов.
3. Проверить вариант с восстановлением index, если поддерживается.
4. Убедиться, что stash после `apply` сохранен.

Отдельно проверить:

- `includeUntracked`;
- отсутствующий stash;
- dirty worktree перед apply;
- отклоненный approval;
- sensitive path.

После этапа выдай отчет.

## Этап 9. Финальная проверка состояния

1. Выполни `git_status`.
2. Убедись, что тестовые операции не повредили исходный репозиторий.
3. Удали тестовые файлы и ветки только разрешенными инструментами.
4. Не удаляй существующие пользовательские данные.
5. Не выполняй `git reset --hard`, `git clean`, `git checkout -f` и прямые shell-команды.

## Итоговый отчет

Сформируй таблицу:

| Категория | Инструмент | Статус | Проверенные сценарии | Обнаруженные проблемы |
| --- | --- | --- | --- | --- |

Статусы:

- `PASS`
- `FAIL`
- `PARTIAL`
- `NOT TESTED`

В конце отдельно перечисли:

1. критические ошибки;
2. ошибки безопасности;
3. нарушения `WorkspaceRoot`;
4. проблемы approval;
5. ошибки structured error handling;
6. инструменты, требующие доработки.

Не исправляй найденные проблемы без отдельного задания.
